# bpmndiff — Progress since `dad107b`

**Presentation source notes · 19 November 2026**

This document summarizes what changed between commit
`dad107b323eda680edb2ee0be2512791931a56ba` and the current `HEAD`
(`9d7fdec`). It is written as raw material for a class presentation, not as a
commit-by-commit changelog.

Use the short version for slides and the detailed sections for speaker notes.

---

## 1. The one-slide summary

> Between these two commits, `bpmndiff` stopped being only a working demo and
> became a **measurable research prototype**: it now has a formal change
> contract, four comparable alignment strategies, a reproducible 30-pair
> benchmark with ground truth, a Precision/Recall/F1 evaluation harness, and
> per-pair reports and figures.

Three sentences to say out loud:

1. **Before:** the tool could compare two BPMN/XPDL models and print an edit
   script, but there was no standard output contract, no ground-truth dataset,
   and no quantitative evaluation.
2. **Now:** every detected change follows a versioned schema, every alignment
   strategy can be compared on the same 30 generated pairs, and the results are
   reproducible from one command.
3. **The main finding:** identifier churn is the dominant failure mode. ID-only
   matching is perfect when IDs survive and collapses when a re-export renames
   every element.

## 2. Before vs. now

| Dimension | At `dad107b` | At current `HEAD` |
|---|---|---|
| Comparison shape | Mode A (pairwise), Mode B (reference vs many), Mode C (version chain) | Pairwise only, with four selectable alignment strategies |
| Alignment | One tiered matcher | `id`, `name`, `structure`, `hybrid` as explicit, comparable modes |
| Output format | Ad-hoc operation records | Versioned `change-v1` contract: `change` + `evidence` layers + runtime invariants |
| Change vocabulary | A handful of operations | 21 canonical operation types across 5 scope categories |
| Test dataset | A few hand-picked demo pairs | 30 generated pairs (5 bases × k = 1/2/4 × kept/regenerated IDs) |
| Ground truth | None | Machine-readable `change-v1` ground truth per pair + manifest |
| Evaluation | Manual inspection | P/R/F1 per change type, per alignment mode, per scenario |
| Reports | Whole-run demo report | Aggregate reports + one JSON and one Markdown report per pair |
| Visualization | None | 6 PNG figures + 1 CSV correlation matrix |
| Tests | 18 tests in 3 files | 84 tests in 10 files |
| Runtime dependencies | Standard library only | Still standard library only; figures are an optional `[viz]` extra |

### What was removed on purpose

Mode B (reference vs many variants) and Mode C (version chain) were dropped.
The project deliberately narrowed its scope to **pairwise comparison done
well**, because the evaluation question — “which alignment signal survives real
BPMN edits?” — only needs a reliable pairwise engine. `bpmndiff/modes.py` was
deleted as part of that decision.

> **Slide line:** “We removed breadth to buy rigor.”

---

## 3. The three big shifts

### 3.1 From “it works” to “it is measured”

Previously, correctness was demonstrated with a handful of nice examples.
Now there is a benchmark: 30 pairs, known edit scripts, and a scorer. A change
to the matcher can be judged by numbers instead of by whether the demo still
looks right.

### 3.2 From ad-hoc output to a versioned contract

Detected changes are no longer just labels and strings. Each record has:

- a canonical `change` layer (type, category, before/after, subtype,
  confidence, review flag), and
- an `evidence` layer (alignment scores, structural context, observations).

A runtime invariant checker rejects inconsistent output instead of silently
emitting it. That makes the JSON safe to consume from other tools.

### 3.3 From demo pairs to a reproducible benchmark

The benchmark is generated, not hand-written. The generator injects controlled
mutations into five real diagrams, rewrites XML IDs when requested, keeps the
BPMN DI plane consistent, and writes the ground truth from the same identity
map used to perform the mutations. Re-running the generator with the same seed
reproduces the dataset.

## 4. What was added

### 4.1 Change taxonomy and output contract

Files: `docs/changes.md`, `docs/taxonomy.md`, `schema/change-v1.json`,
`bpmndiff/contract.py`.

- **21 canonical operation types**, grouped into five stable categories:
  1. Steps (tasks and events)
  2. Actors (lanes and pools)
  3. Sequence, flow, and branching
  4. Sub-process structure
  5. Data and cross-pool communication
- **Two-layer output:** `change` describes what changed; `evidence` explains
  why the tool believes it (alignment scores, matched neighbours, graph facts).
- **Backward compatibility:** legacy fields such as `op` and `legacy_op` are
  still mirrored, but the invariant checker verifies that the mirrors agree.
- **Failure is loud:** schema or invariant violations raise
  `ComparisonInvariantError` rather than producing quietly wrong output.

### 4.2 Four alignment modes

Files: `bpmndiff/alignment.py`, `bpmndiff/cli.py`.

| Mode | Uses | Purpose |
|---|---|---|
| `id` | Shared XML/BPMN IDs | Upper bound when IDs are stable |
| `name` | Label similarity only | Tests how far text alone gets |
| `structure` | Directed topology and neighbourhood context only | Tests structural matching without IDs or labels |
| `hybrid` | IDs → labels → semantic → structural context | The practical default |

These modes turn alignment into an **ablation study**: the same dataset is
scored four ways, so the contribution of each signal is visible.

### 4.3 Synthetic benchmark generator

Files: `bpmndiff/generator.py`, `dataset/synthetic/`, `bpmndiff generate`.

- **5 base diagrams:** `56`, `57`, `58`, `63`, `65` from the converted XPDL
  dataset.
- **3 mutation counts:** `k = 1`, `2`, `4`.
- **2 ID policies:** keep every ID, or regenerate every ID (simulating a
  re-export).
- **Total: 30 pairs.**
- **12 mutation kinds**, including rename (synonym and meaning change), node
  insert/delete, node-type change, lane rename/move, marker change, gateway
  type change, flow condition change, flow insert, and data change.
- **Realistic files:** the generator updates the BPMN DI plane (shapes, edges,
  lane geometry) so mutated files stay valid for BPMN tooling.
- **Manifest:** records pair paths, ID policy, mutation count, ground-truth
  path, and the variant-to-reference `node_map`.

The variants are nested: `k=4` contains the mutations of `k=1` and `k=2`. That
makes it possible to talk about single-edit vs. compound-edit difficulty.

### 4.4 Evaluation harness

Files: `bpmndiff/evaluation.py`, `results/`, `bpmndiff evaluate`.

- Scores every pair against `change-v1` ground truth.
- Normalizes variant IDs back into **reference-ID space** using the manifest
  `node_map`, so a new-ID variant is judged on correspondence, not on the
  random IDs it happens to carry.
- Reports **Precision, Recall, F1, support, TP, FP, FN**:
  - overall,
  - per change type,
  - per alignment mode,
  - per scenario (`keep_ids` vs `new_ids`).
- Writes `pilot.csv`, `pilot_pairs.csv`, `pilot.json`, `pilot_summary.md`, and
  `error_analysis.md`.

### 4.5 Per-pair reports

Files: `bpmndiff/evaluation.py`, `results/pairs/`, `bpmndiff evaluate
--pair-reports`.

Every pair × alignment mode can produce:

- `results/pairs/<mode>/<base>_<variant>.json`
- `results/pairs/<mode>/<base>_<variant>.md`

Each report contains the pair metadata, overall and per-type metrics, false
positives/negatives, normalized predicted and ground-truth operation keys, the
ground-truth operation list, and the full diff (alignment, edit script,
behavioural check, fusion verdict).

The feature is opt-in because `--pair-reports all` would produce
30 pairs × 4 modes × 2 formats = **240 files**. A generated `index.json` lists
them all.

### 4.6 Result figures

Files: `bpmndiff/visualize.py`, `results/figures/`, `bpmndiff visualize`.

Six PNG figures plus one CSV:

| Figure | Message |
|---|---|
| `mode_overall.png` | Precision/Recall/F1 per alignment mode |
| `type_mode_heatmap.png` | Which change types each mode handles |
| `id_churn.png` | The F1 drop caused by ID regeneration |
| `pair_mode_heatmap.png` | Per-pair F1, grouped by base diagram |
| `pair_f1_distribution.png` | Spread of per-pair F1, not just the mean |
| `mode_correlation.png` | How similarly the modes behave |
| `mode_correlation.csv` | The correlation data |

The figures are a reporting layer only. No figure feeds back into the diff, and
the comparison engine still runs on the standard library alone.

## 5. Results

Operation-level metrics over all 30 pairs:

| Alignment mode | F1 (IDs kept) | F1 (IDs regenerated) | F1 (all) | FP | FN |
|---|---:|---:|---:|---:|---:|
| `id` | 1.000 | 0.075 | 0.197 | 687 | 30 |
| `name` | 0.248 | 0.244 | 0.246 | 596 | 18 |
| `structure` | 0.129 | 0.129 | 0.129 | 692 | 62 |
| `hybrid` | 1.000 | 1.000 | 1.000 | 0 | 0 |

Precision/Recall context for the overall column:

| Mode | Precision | Recall |
|---|---:|---:|
| `id` | 0.114 | 0.746 |
| `name` | 0.144 | 0.847 |
| `structure` | 0.075 | 0.475 |
| `hybrid` | 1.000 | 1.000 |

### How to read these numbers

**1. ID churn is the dominant failure mode.**
`id` matching is exact while IDs survive (`F1 = 1.000`) and collapses when they
do not (`F1 = 0.075`). The precision is 0.041 in the `new_ids` scenario: almost
everything it emits is a false positive, because every unmatched node becomes
an insert/delete pair.

> **Slide line:** “The same model, re-exported, breaks ID-only diffing.”

**2. Label matching has good recall but poor precision.**
`name` reaches recall 0.847 but precision 0.144. It finds renames, type changes,
markers, and lane moves reliably, but leaves unnamed gateways and events
unmatched, which creates flow-level false positives around every branch.

**3. Pure structural matching is too strict.**
`structure` reaches only 0.475 recall. Symmetric branches and repeated gateway
shapes are indistinguishable by topology alone, so it skips non-singleton
groups and misses both the node edit and its incident flows.

**4. Hybrid is perfect on this pilot — with an important caveat.**
`hybrid` scores 1.000 in both ID scenarios. That is a **ceiling effect**, not
proof of general correctness: the injected mutations are local and
unambiguous, and each one leaves a redundant combination of ID, label,
structure, and context signals intact. The benchmark is designed to measure
the engine, not to flatter it.

> **Say this explicitly in the presentation:** hybrid’s perfect score is a
> property of this synthetic pilot, not evidence that BPMN diffing is solved.

## 6. Error analysis

The three most frequent failure patterns are all the same operation type —
`INSERT_FLOW` — for three different reasons:

| # | Pattern | Frequency | Why it happens |
|---|---|---:|---|
| 1 | FP `INSERT_FLOW`, mode `name` | 305 | Unnamed gateways/events remain unmatched, so branches look structurally new |
| 2 | FP `INSERT_FLOW`, mode `structure` | 248 | Structural fingerprints are not unique on symmetric or repeated gateway shapes |
| 3 | FP `INSERT_FLOW`, mode `id` (`new_ids`) | 229 | After a full re-export, every node is unmatched, so the real edit is buried in insert/delete noise |

This is a useful story for the class: the failure is not random. It is
concentrated in **flows**, and each mode fails for a different, explainable
reason.

The full analysis with concrete pair examples is in
`results/error_analysis.md`.

## 7. Engineering quality

- **84 tests pass** (up from 18), across 10 test modules.
- The 5 visualization tests skip cleanly when `pandas`/`matplotlib` are absent.
- **No runtime dependencies.** `pip install -e '.[viz]'` is only needed for
  figures.
- **Deterministic generation:** the same seed reproduces the same dataset.
- **Contract tests:** invalid change types are rejected by the schema, and
  legacy-field mismatches fail the runtime invariants.
- **Regression test:** the “invisible task” `Cashier 1` vs `Cashier 2` case is
  locked as a test so it stays a clean `RENAME_NODE` rather than a fake
  delete + insert.
- **CLI is smaller and clearer:** one comparison command with
  `--alignment-mode`, plus `generate`, `evaluate`, and `visualize`.

Run it:

```bash
python3 -m bpmndiff generate
python3 -m bpmndiff evaluate --pair-reports
.venv/bin/python -m bpmndiff visualize   # needs the [viz] extra
python3 -m unittest discover -s tests -v
```

## 8. What this does not claim

Be explicit about scope in the presentation:

- The benchmark is **synthetic**: 5 base diagrams with injected edits. It is
  not a sample of real organizational change histories.
- `hybrid = 1.000` is a **pilot ceiling**, not a general result.
- There is **no external baseline yet** (for example `bpmn-js-differ`).
- There are **no dedicated noise pairs yet** (identical models with only
  re-export noise), which is the cleanest test of false positives.
- The behavioural engine still treats conditions, data, message flows, and
  sub-process interiors as partially compared rather than fully executed.
- SESE decomposition is a dominator-based approximation of a canonical RPST.

From `docs/develop.md`:

## 12. One-paragraph version

Since `dad107b`, `bpmndiff` gained a formal change contract, four comparable
alignment strategies, a deterministic 30-pair synthetic benchmark with
ground-truth edit scripts, a Precision/Recall/F1 evaluation harness, per-pair
JSON/Markdown reports, and six result figures. The old Mode B/C breadth was
removed so the project could focus on pairwise accuracy. The pilot shows that
ID-only alignment is perfect when identifiers survive and collapses under ID
regeneration, while name and structure alignment trade precision for recall.
The hybrid matcher recovers every injected edit on this pilot, but that is a
ceiling effect of a local, unambiguous synthetic benchmark — not a general
correctness claim. Test coverage grew from 18 to 84 tests, and the comparison
engine remains standard-library-only.
